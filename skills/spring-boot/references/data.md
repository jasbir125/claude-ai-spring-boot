# Data Layer: Entities, Repositories, Flyway, Transactions

How a service stores its own data in a relational database. Examples come from `examples/user-service` and `examples/order-service` (PostgreSQL 17, Hibernate 7, Flyway 12).

## Entities

An entity is the aggregate with its rules, not a bag of setters.

```java
@Entity
@Table(name = "users")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)   // only JPA uses the empty constructor
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "email", nullable = false, length = 254)
    private String email;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    private UserStatus status = UserStatus.ACTIVE;

    @CreationTimestamp
    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Version
    @Column(name = "version", nullable = false)
    private Long version;

    public static User register(String email, String displayName) { ... }   // factory with the rules

    /** @return true only on the transition ACTIVE → DEACTIVATED (idempotent) */
    public boolean deactivate() { ... }
}
```

Rules:
- Lombok `@Getter` plus a protected no-args constructor; **no** `@Data`, `@EqualsAndHashCode`, or `@ToString` on entities (they touch lazy associations and break with Hibernate proxies).
- Changes go through methods that enforce the rules (`deactivate`, `cancel`), which return whether anything changed so callers can skip events for no-ops.
- Enums are stored as strings, never ordinals.
- Every entity that clients edit has `@Version` for optimistic locking.
- Map `Instant` to `TIMESTAMPTZ`, money to `NUMERIC(p,s)` with `BigDecimal`.
- Another service's data is referenced **by ID only** (`Long userId`), never with a JPA relation across service boundaries.

## Repositories

```java
public interface UserRepository extends JpaRepository<User, Long> {

    boolean existsByEmail(String email);

    boolean existsByEmailAndIdNot(String email, Long id);

    Page<User> findByStatus(UserStatus status, Pageable pageable);
}
```

- Derived queries for simple cases, `@Query` (JPQL) when the name gets long, native SQL only for database features such as `FOR UPDATE SKIP LOCKED` or `ON CONFLICT`.
- Return `Page` from the repository; the controller wraps it in `PagedModel`.
- For tables without an entity (an inbox), a small `@Repository` class with `JdbcClient` is simpler than a fake entity.

## Avoiding N+1 Queries

Loading a list and then touching a lazy collection per row runs one extra query per row.
- List endpoints return a **summary record** without child collections.
- When the children are needed, fetch them in the same query: `@EntityGraph(attributePaths = "lines")` on the finder, or a `JOIN FETCH` query.
- Do not combine collection fetches with paging in one query (Hibernate then pages in memory); page the parents, then load children for that page with one `IN` query.
- Check the SQL during development (`spring.jpa.show-sql` locally, or a datasource proxy in tests) when a page feels slow.

## Transactions

- Services are `@Transactional(readOnly = true)` at class level; methods that change data add `@Transactional`.
- Keep transactions short: no HTTP calls, no waiting on a broker, no sleeps inside them (the outbox relay's small batch is the documented exception, see `messaging-patterns`).
- Use `saveAndFlush` when the next step needs generated values (ID, incremented `@Version`) in the same transaction, for example before writing an event that carries them.
- With `open-in-view: false`, map entities to DTOs **inside** the service method, while the session is open.

## Optimistic Locking

Two ways a conflict shows up, both become `409`:
1. The client sends the `version` it last read and it no longer matches: throw a domain `VersionConflictException` before changing anything.
2. Two requests change the same row at the same time: Hibernate throws `ObjectOptimisticLockingFailureException` at flush or commit. Do not catch it inside the transaction; let the exception handler map it.

Pessimistic locks (`@Lock(PESSIMISTIC_WRITE)` or `FOR UPDATE`) are for short, explicit critical sections only, such as two flows that must not interleave on one row; document why.

## Database Migrations

Flyway owns the schema; Hibernate only checks it (`ddl-auto: validate`).

Setup:
- Dependencies `spring-boot-starter-flyway` and the database module (for PostgreSQL `flyway-database-postgresql`); defaults need no `spring.flyway.*` settings.
- Scripts live in `src/main/resources/db/migration` as `V<number>__<what_it_does>.sql`.

Writing migrations:
- One new file per change; **never edit a script that has run anywhere**.
- Primary keys are identity columns (`BIGINT GENERATED BY DEFAULT AS IDENTITY` on PostgreSQL), mapped with `GenerationType.IDENTITY`.
- Name every constraint and index: `pk_`, `uk_`, `fk_`, `ck_`, `ix_` + table + column. Error handlers match unique-constraint names, so names are part of the API behaviour.
- Index every foreign-key column and every column used in frequent filters.
- Put validation limits into `CHECK` constraints too (lengths, allowed statuses, positive amounts).
- A new `NOT NULL` column on an existing table needs a `DEFAULT` or a backfill step.
- Column types must match the mapping, or startup fails validation: `VARCHAR(n)` for `String` with `length = n` (not `CHAR`), `TIMESTAMPTZ` for `Instant`, `JSONB` mapped with `@ColumnTransformer(write = "?::jsonb")` for a `String`.

Example (`examples/user-service`, `V1__create_users.sql`):

```sql
CREATE TABLE users (
    id            BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    email         VARCHAR(254) NOT NULL,
    display_name  VARCHAR(100) NOT NULL,
    status        VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',
    created_at    TIMESTAMPTZ  NOT NULL,
    updated_at    TIMESTAMPTZ  NOT NULL,
    version       BIGINT       NOT NULL DEFAULT 0,
    CONSTRAINT pk_users PRIMARY KEY (id),
    CONSTRAINT uk_users_email UNIQUE (email),
    CONSTRAINT ck_users_status CHECK (status IN ('ACTIVE', 'DEACTIVATED'))
);
CREATE INDEX ix_users_status ON users (status);
```

Changing a live schema without downtime (expand → migrate → contract):
1. **Expand:** add the new column or table, nullable or with a default; the old code keeps working.
2. **Migrate:** deploy code that writes both, backfill old rows in batches.
3. **Contract:** in a later release, once nothing reads the old column, drop it.
Renames are always "add new + copy + drop old later", never `RENAME` in one step.

Integration tests run every migration against the real database (Testcontainers) and assert that none is pending (`testing.md`).
